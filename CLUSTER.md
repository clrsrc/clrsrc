# clrsrc Datagen Cluster: Self-Play Data Generation on a Budget

## Why Data Generation?

Modern chess engines rely on NNUE (Efficiently Updatable Neural Networks) for position evaluation. Training an NNUE requires millions of labeled positions — each one a chess position paired with both a search score (the engine's evaluation) and the eventual game result (win/draw/loss).

The quality of training data directly determines the strength of the neural network. Positions must be generated by the engine itself (self-play) so that the scores are consistent with the engine's own search. Using data from a different engine or mixing data from different engine versions degrades training quality — we learned this the hard way when mixed-version data caused a 768-hidden net to lose 20 ELO compared to the same net trained on homogeneous data.

Our target: **60 million positions** generated by v16 of the engine, using NNUE evaluation, with 200K soft node searches per move.

## The Challenge

Professional engine teams (Stockfish, Lc0) use cloud infrastructure or dozens of powerful machines for data generation. We had none of that — just a desktop PC, some old laptops, and a couple of smartphones. The solution was to turn every available compute device into a datagen node, orchestrated remotely via SSH from a single Windows 11 desktop using **Claude Code** as the AI-powered command center.

## Device Setup

### x86 Laptops: Debian Live-USB

The laptops (Notebook, Device33) boot from **USB sticks running Debian 13** — no installation on the internal drive required. This turns any borrowed or unused laptop into a datagen node.

Key optimizations:

- **GNOME desktop removed** — saves ~2GB RAM, critical on the 4GB X230i and 8GB Device33
- **Lid switch disabled** (`HandleLidSwitch=ignore` in logind.conf) — laptops run closed
- **Suspend/hibernate masked** via systemd — no accidental sleep during multi-day runs
- **UPower CriticalPowerAction=Ignore** — prevents shutdown on low battery when running on AC
- **Rust toolchain installed** via rustup — each machine compiles natively with `target-cpu=native` for optimal SIMD utilization (AVX2 on Kaby Lake+, SSE2 on Ivy Bridge)
- **WiFi**: Some devices need external USB WiFi adapters for reliable 5GHz connectivity

### Android Phones: Termux

Smartphones are surprisingly capable datagen nodes. The Snapdragon 778G and Dimensity 9300+ deliver 35-80 pos/s — competitive with Intel laptop CPUs.

Setup:

- **Termux** app provides a full Linux environment with package manager
- **OpenSSH server** on port 8022 (`sshd` in Termux)
- **Rust toolchain** installed natively via `pkg install rust` or rustup
- **Cross-compilation not needed** — the engine compiles directly on-device for aarch64
- **Thermal management**: Thread count tuned per device. The Dimensity 9300+ throttles at 7 threads (clock drops 50%), so 6 threads is optimal. Active cooling (fan/ice pack) helps sustain peak rates.
- **SSH key quirks**: Some older Android SSH implementations require `PubkeyAcceptedAlgorithms rsa-sha2-256` in the SSH config

### Desktop: Windows 11 (Control Node)

The desktop serves dual roles:

- **Datagen node** (8 threads, highest single-thread performance)
- **Control node** running Claude Code, which manages the entire cluster via SSH

Additionally:

- **RTX 5060 Ti GPU** for NNUE training with the Bullet trainer
- **6-piece Syzygy tablebases** for engine testing
- **CuteChess-cli** for ELO testing of engine changes

## SSH Orchestration

All remote machines are configured in `~/.ssh/config` with key-based authentication:

```
Host notebook
    HostName 192.168.0.58
    User youruser
    IdentityFile ~/.ssh/id_rsa

Host x230i
    HostName 192.168.0.45
    User youruser
    IdentityFile ~/.ssh/x230i_key

Host phone
    HostName 192.168.0.27
    Port 8022          # Termux sshd default
    User youruser
    IdentityFile ~/.ssh/id_rsa
```

Starting datagen on a remote machine is a single SSH command:

```bash
ssh notebook "cd ~/clrsrc && source ~/.cargo/env && \
  nohup ./target/release/clrsrc datagen 500000 8 data_v16_notebook.bin 7 book.bin \
  > datagen_v16_notebook.log 2>&1 &"
```

The `nohup` ensures the process survives SSH disconnection. Each machine writes to its own output file to avoid conflicts.

## Datagen Implementation

The datagen module (`src/datagen.rs`) implements multi-threaded self-play:

### Game Flow

1. **Opening**: Use a Polyglot opening book (any standard `.bin`, ours had ~11.6M entries) for diverse starting positions. If no book is available, play 8 random moves. *(The book used during development was assembled from third-party books and is not redistributed with clrsrc.)*
2. **Search**: Each move uses 200K soft nodes / 10M hard nodes (not fixed depth). This produces deeper, higher-quality evaluations than fixed-depth search.
3. **Recording**: Positions are saved in Bullet-compatible format (32 bytes each): occupancy bitboard, packed pieces, search score, game result, king squares, side-to-move.
4. **Filtering**: Skip positions in the first 4 plies after the opening, positions with |score| > 10000cp, and noisy tactical positions (in-check).
5. **Adjudication**: Draw if |score| <= 10cp for 10 consecutive plies after ply 70. Win if |score| >= 3000cp for 5 consecutive moves.

### Multi-Threading

Each thread runs independent games with:

- **Separate transposition tables** — no cross-contamination between games
- **Shared NNUE weights** via `Arc` — loaded once, used by all threads
- **Per-thread stop flag** — avoids the global stop race condition we fixed in v16
- **Atomic counters** for progress tracking across threads
- **Flush every 10 games** — small enough to not lose much data on crashes, but not so frequent as to bottleneck I/O

### CLI

```
clrsrc datagen <games> <depth> <output.bin> <threads> [book.bin]
```

The `depth` parameter is legacy — search is now node-limited (200K/10M soft/hard).

## Cluster Monitoring

A Python monitoring script (`tools/datagen_status.py`) queries all machines in parallel using persistent SSH connections (paramiko):

```bash
python tools/datagen_status.py 60          # single snapshot with 60s delta
python tools/datagen_status.py 60 --watch  # continuous monitoring
```

Output:

```
desktop:   3094904 pos ( 94 MB) |  72 pos/s
notebook:  6469884 pos (197 MB) |  64 pos/s
phone:     4633849 pos (141 MB) |  35 pos/s
x230i:     1993284 pos ( 60 MB) |  24 pos/s
xiaomi:    3273734 pos ( 99 MB) |  65 pos/s
device33:   475049 pos ( 14 MB) |  27 pos/s
---
Total:    19940704 pos | 291 pos/s | 33% | ETA 60M: 38h (~1d 14h)
```

The script works by taking two file-size measurements separated by the delta interval, then computing positions/second from the byte difference (each position = 32 bytes).

## Collecting Data

Each machine writes its data locally. Collection happens via `scp`:

```bash
scp notebook:~/clrsrc/data_v16_notebook.bin .
scp phone:~/clrsrc/data_v16_phone.bin .
scp device33:~/clrsrc/data_v16_device33.bin .
```

For the final training dataset, all files are concatenated:

```bash
cat data_v16_*.bin > data_v16_combined.bin
```

The Bullet format is append-friendly — files can be concatenated and the trainer reads them correctly.

## Training

NNUE training uses the [Bullet trainer](https://github.com/jw1912/bullet), a GPU-accelerated NNUE trainer written in Rust:

### Architecture

- **Input**: 768 features (2 colors x 6 piece types x 64 squares), perspective-based (HalfKP-like)
- **Hidden layer**: 768 neurons, incrementally updated
- **Activation**: SCReLU (Squared Clipped ReLU): `clamp(x, 0, 255)^2`
- **Output**: Single neuron, scaled to centipawns
- **Quantization**: Feature weights QA=255, output weights QB=64

### Training Command

```bash
cd bullet
CARGO_TARGET_DIR=C:/temp/bullet_target cargo +nightly run --release --example clrsrc
```

The `CARGO_TARGET_DIR` workaround prevents Dropbox from locking build artifacts.

### Training Config

- **GPU**: NVIDIA RTX 5060 Ti (CUDA 12.8)
- **Data**: 60M positions (~1.8 GB)
- **Schedule**: 120 superbatches, 7324 batches per superbatch
- **Training time**: ~30 minutes for 768-hidden
- **Output**: Binary NNUE file (e.g., `clrsrc_v11.nnue`, ~1.2 MB)

### Key Training Insights

- 768 hidden neurons with 60M positions = **+26 ELO** over 512 hidden (only 12% NPS cost)
- 1024 hidden with same data = +4 ELO over 768 (not significant — diminishing returns)
- Data quality matters more than quantity: 60M homogeneous positions beat 116M mixed-version positions
- Minimum viable dataset: ~60M positions for 768-hidden. Below 31M, the net regresses.

## The Role of Claude Code

This entire cluster operation — from initial setup to ongoing management — is orchestrated through **[Claude Code](https://docs.anthropic.com/en/docs/claude-code)**, Anthropic's AI-powered CLI assistant. Without it, managing a heterogeneous cluster of 6+ devices across three operating systems (Windows, Linux, Android) would be impractical for a solo developer.

### What Claude Code Does

- **Remote deployment**: Compiles the engine on each machine via SSH, handling different cargo/PATH configurations per OS
- **Process management**: Starts/stops datagen with correct parameters per machine, uses `nohup` for persistence
- **Monitoring**: Runs the status script, interprets results, identifies problems
- **Diagnostics**: Reads CPU features, kernel logs, thermal sensors, and process stats across all machines to diagnose performance issues (e.g., detecting that x230i's low throughput was due to missing AVX2 integer SIMD on Ivy Bridge, not thermal throttling)
- **Optimization**: Tunes thread counts per device based on measured throughput and thermal behavior (e.g., discovering the Dimensity 9300+ throttles at 7 threads)
- **Build configuration**: Sets up `.cargo/config.toml` with `target-cpu=native` on each machine for optimal SIMD auto-vectorization
- **Code changes**: Implements engine features, fixes bugs (like the multi-threaded stop-flag race condition), writes the monitoring script
- **Training pipeline**: Configures the Bullet trainer, runs training, evaluates results via ELO testing
- **Memory across sessions**: Maintains persistent knowledge about the machine fleet, tuning results, and project state across conversations — essential for multi-day operations

### The Workflow

A typical session looks like this:

1. **"Starte datagen auf allen Geraeten"** — Claude Code SSHs into each machine, checks binary freshness, compiles if needed, starts datagen with optimal thread counts
2. **"Wie ist der Status?"** — Runs the monitoring script, reports rates and ETA
3. **"X230i ist langsam"** — Investigates CPU features, thermal sensors, compile flags, identifies root cause, applies fix
4. **"Sammle Daten ein und trainiere"** — SCPs data from all machines, concatenates, runs Bullet trainer, evaluates new net via gauntlet

This conversational workflow turns what would be a complex sysadmin + ML engineering task into a natural dialogue. The AI handles the tedious parts (SSH commands, path differences, environment setup) while the developer focuses on high-level decisions (thread counts, training architecture, ELO testing).

## Lessons Learned

1. **Smartphones are viable compute nodes.** A modern phone CPU with Termux delivers laptop-class throughput for integer-heavy workloads like chess search.
2. **USB Live Linux is a game-changer.** Any spare laptop becomes a datagen node in minutes — boot from USB, install Rust, start generating.
3. **Compile natively, don't cross-compile.** Each architecture has its own SIMD capabilities. Native compilation with `target-cpu=native` lets LLVM auto-vectorize optimally. But beware: AVX2 is needed for i16 integer vectorization — older CPUs (Ivy Bridge) with only AVX see no improvement because AVX is float-only.
4. **Thread count requires per-device tuning.** Mobile SoCs throttle aggressively. Measure actual throughput at different thread counts — the theoretical maximum is rarely the practical optimum.
5. **Homogeneous data beats diverse data.** Train on positions from one engine version. Mixed-version data introduces score inconsistencies that hurt smaller nets.
6. **An AI assistant makes it feasible.** Managing 6 heterogeneous devices across 3 operating systems as a solo developer is only practical with an AI that remembers the fleet configuration, handles SSH orchestration, and diagnoses issues across architectures.
